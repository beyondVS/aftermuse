# General Library & Module Rules (범용 라이브러리 및 패키지 아키텍처 규칙)

언어와 생태계에 국한되지 않고 모든 공용 라이브러리, 모듈, SDK 개발 프로젝트에 공통으로 적용되는 기본 설계 및 품질 관리 규칙입니다.

---

## 📦 1. 인터페이스 설계 및 하위 호환성 (API Design & SemVer)

- **명확한 Public API 분리**: 외부에 노출되는 공용 모듈(Public Interface)과 내부 구현 모듈(Internal Implementation)을 엄격히 구분하고, 명시적인 인터페이스를 통해서만 노출하십시오.
- **Breaking Change 최소화**: 공개 API 변경이 기존 소비자에게 미치는 영향을 확인하고 프로젝트가 채택한 deprecation·version 정책에 따라 전환하십시오. SemVer를 채택한 프로젝트에서만 호환성 영향에 맞는 version 단계를 적용하십시오.
- **Side-Effects 최소화**: 모듈 임포트 시 글로벌 상태를 직접 변경하거나 예기치 않은 부작용(Side Effect)이 발생하지 않도록 순수 함수(Pure Functions) 중심 설계를 지향하십시오.

---

## 🧪 2. 테스트 격리 및 문서화 (Testing & Documentation)

- **계약 기반 테스트**:
  Public API의 계약과 위험에 맞춰 unit, integration, contract test를 조합합니다.
  외부 환경을 격리할 수 있는 단위 테스트는 사용하되, 실제 통합 동작을 검증해야 하는 계약까지 100% 단위 테스트로 제한하지 않습니다.
- **인터페이스 문서화**: 공개 인터페이스는 Core의 코드 문서화 및 주석 기준에 따라 책임과 계약을 문서화합니다.
  사용 예시가 소비자의 올바른 사용이나 호환성 이해에 필요하면 패키지의 공식 API 문서에 포함하고, 표현 형식은 언어별 style 규칙을 따릅니다.

---

## 🚀 3. 의존성 관리 및 독립성 (Dependencies & Packaging)

- **최소 의존성 원칙 (Minimal Dependencies)**: 무거운 외부 라이브러리 추가를 최소화하여 설치 용량과 보안 취약점 노출을 줄이십시오.
- **명확한 의존성 분리**: 런타임 의존성(Dependencies)과 개발/테스트 전용 의존성(Dev Dependencies)을 엄격히 구분하십시오.
- **독립 설치 스펙 준수**: 라이브러리가 타 시스템이나 프로젝트에 모듈로 통합될 때 예기치 않은 전역 상태 오염이나 내부 경로 결합이 발생하지 않도록 캡슐화하십시오.

---

## ⚖️ 4. 외부 패키지 도입 vs 자체 구현 의사결정 (In-House vs. External Package Decision)

신규 패키지 설치 시 "자체 구현(In-House)"과 "외부 패키지(External Package) 도입" 간의 선택은 다음 기준과 검증 프로세스를 거쳐 정립하십시오.

### 📊 1) 의사결정 기준 (Decision Matrix)

| 평가 항목 | 자체 구현 (In-House) 우선 | 외부 패키지 (External Package) 도입 |
| :--- | :--- | :--- |
| **코드 규모/복잡도** | 요구사항·변경 빈도·테스트 및 장기 유지 비용이 작고 프로젝트 특화인 기능 | 암호화, 보안 표준, 복잡한 parser 또는 직접 구현 시 회귀·호환성 위험이 큰 기능 |
| **프레임워크 제공 여부** | 프레임워크 내장 기능(예: Django Auth/ORM, React State 등)으로 대응 가능할 때 | 표준 범주를 벗어나 전문 시스템 연동(OAuth2, S3 SDK, Celery 등)이 필수일 때 |
| **커스텀 및 변경 빈도** | 비즈니스 로직에 결합되어 프로젝트 특화 커스텀 변경이 잦을 때 | 표준 스펙 규격이라 직접 구현 시 회귀 버그 및 기술 부채 위험이 클 때 |

### 🛡️ 2) 위험 비례 패키지 건전성 검토 (Package Health & Suitability)

에이전트가 내부 구현을 위해 신규 외부 패키지를 선택할 때는 작업의 위험도에 비례하여 필요한 건전성을 점검합니다. 모든 패키지에 동일한 장문의 정형화된 4대 평가 보고서를 의무 작성할 필요는 없으며, 다음 항목의 실질적 위험 여부를 확인합니다:

1. **유지보수 상태 (Maintenance)**: 지원 대상 런타임과 보안 이슈에 지속적으로 대응할 수 있는 활성 상태인가?
2. **라이선스 호환성 (License)**: 프로젝트의 라이선스 및 상용 배포 조건과 충돌이 없는가?
3. **보안 취약점 (Security)**: 알려진 중대한 보안 취약점(CVE 등)이 없는가?
4. **런타임 및 의존성 영향 (Compatibility & Transitive Deps)**: 프로젝트 런타임/지원 버전과 호환되며, 과도한 전이적 의존성이나 운영 부담을 유발하지 않는가?
5. **아키텍처 결합도 (Lock-in)**: 향후 교체나 확장이 극히 어려운 강한 장기 종속성을 유발하지 않는가?

### 🔄 3) 지시 구분 및 사용자 승인 경계 (Decision Gate & Implementation)

패키지 건전성 평가와 사용자 승인(User Approval)은 분리된 판단입니다:

- **사용자가 특정 패키지를 직접 지시한 경우**:
  사용자가 특정 패키지 사용을 이미 지시했다면(예: "httpx를 사용하라", "Pydantic을 추가하라"), Task-level Authorization에 따라 패키지 도입 의도는 이미 승인된 것입니다. 동일한 설치 승인을 사용자에게 다시 질문하지 마십시오.
- **에이전트가 내부 구현을 위해 선택한 경우**:
  프로젝트 내부 구현 권한 안에서 가역적으로 선택 가능하고 아래의 미해결 우려(unresolved concerns)가 없다면, 불필요한 사전 승인 질문을 추가하지 않고 패키지 매니저(`uv`, `npm`, `pnpm` 등)를 통해 런타임/개발 그룹을 구별하여 추가합니다.
- **사용자 판단 에스컬레이션 (Decision Gate)**:
  다음과 같이 작업 결과나 장기 계약을 실질적으로 바꾸는 미해결 우려가 확인된 경우에만 사용자에게 상황과 대안을 보고하고 승인을 얻습니다:
  - 프로젝트 라이선스와의 잠재적 충돌
  - 알려진 중대한 보안 취약점
  - 프로젝트 지원 런타임/버전과의 비호환성
  - 과도한 전이적 의존성 유입 또는 심각한 운영/빌드 부담
  - 공개 인터페이스나 시스템 아키텍처 계약을 근본적으로 바꾸는 장기 종속성(Lock-in)
  - 복수의 유력한 대안 사이에 제품/설계 관점의 중요한 trade-off가 남아 있는 경우
- **자체 구현 선택 시**:
  프로젝트 아키텍처에 일관된 구조로 캡슐화하고 유지보수성을 확보하십시오.
