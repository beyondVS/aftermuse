# 기능 사양: Interview 상호작용 완결과 Reflection 생성 Transition

**기능 브랜치**: `feature/day-11-interview-reflection-transition`

**생성일**: 2026-09-16

**상태**: 초안

**입력**: 사용자 설명: "11일자 구현 계획 `Day 11 — Interview 상호작용 완결과 Reflection 생성 Transition` 진행을 위한 명세를 만든다."

## Clarifications

### Session 2026-09-16

- Q: 모든 질문을 건너뛰어 확정 답변이 하나도 없는 상태에서 질문 한도에 도달하면 Interview를 어떻게 종료해야 합니까? → A: Reflection 없이 Interview를 종료하고, 답변 부족으로 독서노트가 생성되지 않았음을 안내한다.
- Q: Day 11에서 Reflection 생성에 성공했지만 Day 12의 정식 결과 화면은 아직 구현되지 않은 경우, 사용자를 어디로 이동시켜야 합니까? → A: 생성된 Reflection의 존재와 성공을 보여주는 최소 임시 결과 화면으로 자동 이동한다.

## 사용자 시나리오 및 테스트 *(필수)*

### 사용자 스토리 1 - 답변을 지키며 Reflection 생성 완료하기 (우선순위: P1)

사용자는 Interview를 끝내기로 선택했거나 질문 한도에 도달했을 때 자신의 답변으로 Reflection 생성을 시작하고, 진행 상태를 확인한 뒤 생성 성공을 확인하는 최소 결과 화면으로 이동한다. 생성이 실패해도 지금까지의 답변은 그대로 남고 사용자가 원할 때 다시 시도할 수 있다.

**우선순위가 높은 이유**: Interview가 실제 독서 기록으로 이어지는 핵심 전이이며, 실패 시 답변 보존과 안전한 재시도가 제품 신뢰를 좌우한다.

**독립 테스트**: Reflection 생성 준비가 끝난 Interview에서 생성 성공·실패·재시도를 각각 실행하고, 화면 상태와 최소 임시 결과 화면, 답변 및 Reflection 수를 확인한다. 정식 결과 화면의 상세 레이아웃이나 편집 기능 없이도 전이 자체를 검증할 수 있다.

**인수 시나리오**:

1. **Given** 사용자가 Soft Stop에서 Interview 종료를 선택한 상태, **When** Reflection 생성을 시작하면, **Then** 생성 중임을 명확히 알 수 있고 같은 화면에서 중복 생성 요청을 할 수 없다.
2. **Given** 질문 수 또는 안전 한도에 도달해 Reflection 생성 준비가 된 Interview, **When** 생성이 성공하면, **Then** 같은 Interview에 연결된 단일 Reflection이 보존되고 사용자는 생성 성공과 Reflection의 존재를 확인할 수 있는 최소 임시 결과 화면으로 자동 이동한다.
3. **Given** Reflection 생성 중 오류가 발생한 상태, **When** 실패 결과가 표시되면, **Then** 사용자는 이해 가능한 오류 안내와 다시 시도할 수 있는 행동을 보고 기존 질문·답변은 모두 유지된다.
4. **Given** 앞선 생성이 실패한 Interview, **When** 사용자가 다시 시도해 생성이 성공하면, **Then** 기존 답변을 근거로 단일 Reflection이 생성되고 최소 임시 결과 화면으로 자동 이동한다.
5. **Given** 같은 Interview에 대한 반복 요청 또는 이미 생성된 Reflection, **When** 생성 행동이 다시 전달되면, **Then** 중복 Reflection이나 기존 초안 덮어쓰기 없이 기존 결과로 안전하게 수렴한다.
6. **Given** 다른 사용자의 Interview 또는 생성 조건을 충족하지 않은 Interview, **When** 생성이나 재시도를 요청하면, **Then** 해당 기록에 접근하거나 상태를 바꾸지 못하고 기존 데이터가 유지된다.

### 사용자 스토리 2 - 답하기 어려운 질문 건너뛰기 (우선순위: P1)

사용자는 현재 질문에 답하기 어렵거나 답하고 싶지 않을 때 답변을 꾸며내거나 빈 답변을 제출하지 않고 질문을 명시적으로 건너뛸 수 있다. 건너뛴 뒤에는 다음 질문 또는 Interview 종료 판단으로 자연스럽게 이어진다.

**우선순위가 높은 이유**: 모든 질문에 답해야 한다는 압박을 줄이면서도 실제 답변과 미응답을 구분해야 Coverage와 Reflection의 신뢰성을 지킬 수 있다.

**독립 테스트**: 답변 대기 중인 질문을 건너뛰고 명시적인 Skip 기록, 답변 부재, 다음 질문 또는 종료 전이, Coverage 불변을 확인한다. Reflection 생성 기능과 별도로 검증할 수 있다.

**인수 시나리오**:

1. **Given** 답변을 기다리는 현재 질문, **When** 사용자가 건너뛰기를 선택하면, **Then** 빈 답변을 저장하지 않고 해당 질문이 사용자가 건너뛴 질문으로 구분된다.
2. **Given** 아직 질문을 계속할 수 있는 Interview, **When** 현재 질문을 건너뛰면, **Then** 다음 질문으로 진행하고 건너뛴 항목만으로 충족되지 않은 Coverage가 높아지지 않는다.
3. **Given** 질문 수 또는 안전 한도에 도달한 Interview, **When** 현재 질문을 건너뛰면, **Then** 추가 질문 대신 기존 종료 정책에 따라 Soft Stop 또는 Reflection 생성 준비 상태로 전이한다.
4. **Given** 사용자가 "모르겠어요"처럼 실제 텍스트를 제출한 경우, **When** 답변이 처리되면, **Then** 명시적 Skip이 아닌 실제 답변으로 보존되고 저정보 답변 정책에 따라 다음 단계가 결정된다.
5. **Given** 이미 답변했거나 건너뛴 질문, **When** 동일 행동이 반복 전달되면, **Then** 두 상태가 동시에 생기거나 질문 수가 중복 증가하지 않고 현재 Interview 상태로 안전하게 수렴한다.
6. **Given** 사용자가 모든 질문을 건너뛰어 확정 답변 없이 질문 한도에 도달한 경우, **When** 마지막 Skip이 처리되면, **Then** Reflection을 만들지 않고 Interview를 종료하며 독서노트를 생성하지 못한 이유를 안내한다.

### 사용자 스토리 3 - 내부 상태 대신 친화적인 안내로 Interview 진행하기 (우선순위: P2)

사용자는 책에 대해 확인 가능한 정보가 충분하거나 제한적이어도 내부 상태명이나 기술 용어를 보지 않고 상황을 이해한 채 Interview를 시작하고 진행한다. 정보가 제한적일 때 AI는 책 내용을 아는 척하지 않고 사용자의 기억과 감상을 중심으로 질문한다.

**우선순위가 높은 이유**: 내부 준비 상태를 오류처럼 노출하지 않으면서 정보가 적은 책도 핵심 제품 흐름에서 배제하지 않아야 한다.

**독립 테스트**: 도서 정보가 충분한 상태와 제한적인 상태로 Interview 시작 및 질문 화면을 각각 표시하고 안내 문구와 질문 전제를 확인한다. Reflection 생성이나 Skip 기능 없이도 검증할 수 있다.

**인수 시나리오**:

1. **Given** 도서 정보가 충분한 Interview, **When** 시작 화면과 질문 화면을 보면, **Then** 내부 상태명 없이 자연스러운 시작 안내와 현재 질문을 확인할 수 있다.
2. **Given** 도서 정보가 제한적인 Interview, **When** 사용자가 시작 화면과 질문 화면을 보면, **Then** 시스템 결함이 아니라 확인 가능한 정보가 많지 않다는 친화적인 안내를 받고 Interview를 계속할 수 있다.
3. **Given** 도서 정보가 제한적인 Interview, **When** 질문이 제시되면, **Then** 확인되지 않은 줄거리·인물·주장을 사실로 단정하지 않고 사용자의 기억·인상·경험을 묻는다.
4. **Given** 사용자에게 보이는 Interview 접점, **When** 화면 문구를 확인하면, **Then** 내부 enum, 준비도 명칭, 검색 증강 관련 기술 용어가 직접 노출되지 않는다.

### 예외 상황

- 사용자가 생성 버튼을 빠르게 여러 번 누르거나 동일 요청이 동시에 도착해도 같은 Interview에 둘 이상의 Reflection이 생기거나 기존 Reflection이 바뀌지 않는다.
- 생성 성공 응답을 사용자가 받지 못해 다시 시도해도 이미 저장된 Reflection을 재사용하고 중복 생성하지 않는다.
- 생성 실패, 시간 초과, 유효하지 않은 생성 결과 또는 구성 오류는 성공으로 표시하지 않으며 답변 원문, 외부 응답, credential 및 내부 예외 내용을 사용자 오류 문구에 노출하지 않는다.
- 생성에 실패한 뒤 페이지를 다시 열어도 기존 Interview 답변과 재시도 가능 상태를 복구할 수 있다.
- 확정 답변이 없거나 모두 건너뛴 Interview는 근거 없는 Reflection을 만들지 않고 종결하며, 답변 부족으로 독서노트를 생성하지 않았음을 안내한다.
- 마지막으로 남은 질문을 건너뛴 경우에도 질문 수와 안전 한도를 넘기지 않고 기존 종료 정책에 따라 전이한다.
- Skip 요청과 답변 제출이 경합하면 하나의 최종 상태만 인정하며 답변과 Skip을 동시에 기록하지 않는다.
- 권한이 없거나 현재 Interview에 속하지 않는 질문의 Skip 요청은 어떤 질문·답변·Coverage도 변경하지 않는다.
- 도서 정보가 제한적이라는 사실은 Interview 진입을 영구 차단하지 않으며, 안내 문구는 실패나 사용자 책임을 암시하지 않는다.

## 요구사항 *(필수)*

### 기능 요구사항

- **FR-001**: 시스템은 Soft Stop에서 사용자가 종료를 선택했거나 질문 수·안전 한도에 도달한 Interview를 후속 종결 흐름으로 전환해야 한다. 확정 답변이 하나 이상이면 Reflection 생성 준비 상태로 전환하고, 확정 답변이 없으면 FR-020에 따라 Reflection 없이 종결해야 한다.
- **FR-002**: 시스템은 Reflection 생성 중임을 명확한 상태와 상태 문구로 표시하고, 생성이 끝나기 전 동일 화면에서 중복 생성 행동을 방지해야 한다.
- **FR-003**: 생성 성공 시 같은 Interview에 연결된 유효한 Reflection을 보존하고, 생성 성공과 해당 Reflection의 존재를 확인할 수 있는 최소 임시 결과 화면으로 자동 전환해야 한다.
- **FR-004**: 생성 실패 시 이해 가능한 오류 안내와 명시적인 다시 시도 행동을 제공해야 하며, 사용자의 기존 질문·답변·Coverage·Reading 관계를 변경하거나 삭제해서는 안 된다.
- **FR-005**: 재시도는 실패 전과 동일한 확정 답변을 생성 근거로 사용해야 하며, 사용자의 명시적 행동 없이 자동으로 반복하거나 다른 유료 생성 방식으로 전환해서는 안 된다.
- **FR-006**: 반복·동시 생성 요청과 성공 응답 유실 후 재요청은 Interview당 최대 하나의 Reflection으로 수렴해야 하며, 기존 초안이나 사용자 수정본을 덮어써서는 안 된다.
- **FR-007**: 이미 Reflection이 있는 Interview의 생성 요청은 새 결과를 만들지 않고 소유자가 기존 결과로 계속할 수 있게 해야 한다.
- **FR-008**: 생성 및 재시도는 인증된 소유자의 생성 준비가 끝난 Interview로 제한해야 하며, 타인의 기록이나 부적합한 상태의 기록을 조회·변경하지 않아야 한다.
- **FR-009**: 생성 오류 안내와 진단 정보에는 credential, 답변 원문, 외부 생성 응답 및 내부 예외 원문을 노출하지 않아야 한다.
- **FR-010**: 답변 대기 중인 현재 질문에는 명시적인 건너뛰기 행동을 제공해야 하며, 사용자는 답변 입력 없이 한 번의 행동으로 건너뛸 수 있어야 한다.
- **FR-011**: 사용자 Skip은 빈 문자열, 저정보 텍스트 답변 및 답변 후 다음 질문 생략과 구분되는 명시적 상태로 보존되어야 한다. Skip된 질문에는 Answer를 만들지 않아야 한다.
- **FR-012**: 질문 하나는 확정 답변 또는 사용자 Skip 중 최대 하나의 최종 상태만 가져야 하며, 반복·경합 요청으로 질문 수나 상태 전이가 중복 적용되지 않아야 한다.
- **FR-013**: Skip된 질문은 충족된 Coverage의 근거로 계산하지 않아야 하며, Skip 후에는 기존 질문 생성·질문 수·안전 한도·Soft Stop 정책에 따라 다음 질문 또는 종료 상태로 진행해야 한다.
- **FR-014**: Skip은 현재 사용자와 현재 Interview에 속한 답변 대기 질문으로 제한해야 하며, 이미 확정된 질문이나 타인의 질문에 대한 요청은 기존 데이터를 변경하지 않아야 한다.
- **FR-015**: 사용자에게 보이는 Interview 시작·질문·상태 안내에는 `READY`, `READY_LIMITED`, `Knowledge readiness`, `RAG` 또는 이에 준하는 내부 상태명과 기술 용어를 직접 노출하지 않아야 한다.
- **FR-016**: 도서 정보가 제한적인 상태는 실패로 표현하거나 Interview 시작을 차단해서는 안 되며, 확인 가능한 정보가 많지 않아 사용자의 기억과 감상을 중심으로 진행한다는 친화적인 안내를 제공해야 한다.
- **FR-017**: 도서 정보가 제한적인 Interview의 질문은 확인되지 않은 책 내용·인물·주장·평가를 사실로 전제하지 않아야 하며 사용자가 직접 표현한 기억·인상·경험을 우선해야 한다.
- **FR-018**: Loading, 실패, Retry 및 Skip 상태는 색상만으로 구분하지 않고 명확한 텍스트와 키보드로 접근 가능한 행동을 제공해야 하며 대표 Desktop과 Mobile 폭에서 핵심 행동을 사용할 수 있어야 한다.
- **FR-019**: 이번 범위는 IMP-092의 Reflection 생성 전이와 최소 임시 결과 화면, IMP-095의 사용자용 Knowledge 표현 및 IMP-096의 질문 Skip이다. 정식 Reflection 결과 화면의 본문 읽기 레이아웃·수정·최종 완료, Home 재진입, Credit 처리, 공개·공유, 복잡한 백그라운드 폴링, Skip 취소·되돌리기 및 질문 재생성 분기는 포함하지 않는다.
- **FR-020**: 질문 한도에 도달했을 때 확정 답변이 하나도 없으면 Reflection 생성 흐름에 진입하지 않고 Interview를 Reflection 없는 결과로 종결해야 하며, 사용자에게 답변 부족으로 독서노트를 생성하지 않았음을 안내해야 한다.

### 핵심 엔터티 *(기능에 데이터가 포함되는 경우 작성)*

- **Reflection 생성 시도**: 생성 준비가 끝난 Interview의 확정 답변으로 Reflection 생성을 요청한 한 번의 사용자 행동이다. 진행 중, 성공 또는 실패 결과를 가지며 실패 자체가 Interview 답변을 변경하지 않는다.
- **Reflection**: 한 사용자의 Interview에 최대 하나가 연결되는 독서 기록 초안이다. 반복 및 재시도 요청은 새 Reflection이 아니라 동일한 결과로 수렴한다.
- **사용자 Skip**: 사용자가 특정 Interview 질문에 답하지 않기로 명시적으로 선택한 최종 상태다. 실제 답변, 빈 제출 및 답변 후 다음 질문 생략과 구분된다.
- **Reflection 없는 Interview 종결**: 질문 한도까지 확정 답변이 없어 생성 근거가 없는 Interview의 종결 결과다. Reflection과 완료된 독서노트가 없으며, 생성 실패나 재시도 대기 상태와 구분된다.
- **도서 정보 안내 수준**: 질문에 사용할 수 있는 도서 정보의 충분함 또는 제한됨을 나타내는 내부 판단이다. 사용자에게는 기술 상태명이 아니라 진행 방법을 설명하는 안내로 표현된다.

## 성공 기준 *(필수)*

### 측정 가능한 결과

- **SC-001**: Soft Stop 종료와 질문 한도 도달의 대표 시나리오 100%에서 사용자는 생성 중 상태를 확인하고, 생성 성공 후 같은 Interview의 Reflection 존재와 성공을 보여주는 최소 임시 결과 화면에 자동으로 도달한다.
- **SC-002**: 생성 실패·시간 초과·유효하지 않은 결과·재시도의 대표 시나리오에서 기존 질문·답변·Coverage의 유실 또는 변경은 0건이며, 모든 실패 상태에서 사용자가 다시 시도할 수 있다.
- **SC-003**: 동일 Interview에 대한 반복 요청, 동시 요청, 성공 응답 유실 후 재요청의 대표 시나리오에서 최종 Reflection은 정확히 1개이고 기존 초안 및 수정본 덮어쓰기는 0건이다.
- **SC-004**: 답변 대기 질문의 Skip 시나리오 100%에서 한 번의 사용자 행동 후 다음 질문 또는 종료 상태가 표시되고, 빈 Answer 생성과 답변·Skip 동시 기록은 0건이다.
- **SC-005**: Skip, 저정보 텍스트 답변 및 답변 후 다음 질문 생략의 대표 사례 100%가 서로 구분되며, Skip만으로 충족 Coverage가 증가하는 사례는 0건이다.
- **SC-006**: READY와 READY_LIMITED 대표 fixture 각각에서 Interview 시작 화면과 질문 화면이 정상 응답하고 핵심 진행 행동을 제공해야 한다. 해당 화면의 사용자 노출 문자열에서 내부 상태명과 기술 용어는 0건이어야 하며, READY_LIMITED도 오류 상태로 표현하거나 진행을 차단하지 않아야 한다.
- **SC-007**: 도서 정보가 제한적인 대표 질문 표본에서 확인되지 않은 책 사실을 전제로 한 질문은 0건이고, 모든 질문이 사용자의 기억·인상·경험으로 답할 수 있다.
- **SC-008**: 생성·Retry·Skip의 대표 흐름에서 사용자가 행동을 시작하면 외부 요청 완료를 기다리지 않고 Loading 또는 disabled 상태가 즉시 표시되며, 주요 행동은 키보드로 실행할 수 있다. 대표 Desktop·Mobile breakpoint에서 핵심 행동이 숨겨지거나 viewport 밖으로 강제되지 않아야 한다.
- **SC-009**: 타인 기록, 부적합한 Interview 상태 및 이미 확정된 질문에 대한 거부 시나리오에서 데이터 변경과 민감한 오류 정보 노출은 0건이다.
- **SC-010**: 모든 질문을 건너뛴 대표 시나리오에서 Interview는 Reflection 없이 종결되고, 생성된 Reflection과 빈 독서노트는 0개이며 종결 이유가 사용자에게 표시된다.

## 가정

- 기준 문서는 [PRD §7.3–7.4 및 §13.3–13.4](../../docs/AfterMuse_MVP_PRD_v4.md), [Architecture Decisions의 상태 모델과 Core MVP 원칙](../../docs/AfterMuse_Architecture_Decisions_v4.md), [UI/UX Guide의 Interview·Loading/Error/Retry 기준](../../docs/AfterMuse_UI_UX_and_Design_Implementation_Guide_v8.md), [구현 계획 Day 11](../../docs/AfterMuse_MVP_Implementation_Plan_v5.md)이다. 이번 명세는 기존 제품 정책을 변경하지 않는다.
- Day 10에서 Interview당 단일 Reflection, 확정 답변 기반 초안 생성, 기존 초안·수정본 보존 및 생성 준비 상태가 제공되었다고 가정한다.
- 생성 준비 상태로 진입하는 기존 경로는 Soft Stop 종료 선택과 질문 수·안전 한도 도달이다. 사용자가 아직 더 이야기하기를 선택한 경우에는 생성 흐름으로 이동하지 않는다.
- 생성 성공 뒤 Reflection의 존재와 성공을 보여주는 최소 임시 결과 화면으로 자동 이동하는 연결은 이번 범위에 포함한다. 정식 결과 화면의 본문 읽기 레이아웃·수정·최종 확인·Home 이동은 Day 12 범위다.
- 실패한 생성은 자동 재시도하지 않는다. 사용자가 Retry를 선택할 때만 새 시도를 시작하며, 기존 Reflection이 확인되면 이를 재사용한다.
- 모두 Skip되어 확정 답변이 없는 Interview는 Reflection 생성 근거가 부족한 것으로 처리해 Reflection 없이 종결한다. 별도의 빈 Reflection이나 도서 정보만으로 채운 Reflection을 만들지 않으며, 이 종결 결과는 생성 실패·Retry 상태와 구분한다.
- 사용자 Skip은 단방향 상태다. Skip 취소, 이전 질문으로 돌아가기 및 Skip된 질문 재생성은 이번 범위에 포함하지 않는다.
- 실제 브라우저 조작은 이번 명세의 필수 완료 조건이 아니다. 반응형·접근성·상태 전이는 결정적인 화면 응답과 상태 계약으로 우선 검증하며, 선택형 인간 UX 확인은 구현 완료 판정과 분리한다.
