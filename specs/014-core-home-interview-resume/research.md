# Day 09 설계 조사

## 결정 1: 공개 Home과 개인 허브를 같은 경로에서 구분

- **결정**: `/`는 공개 소개와 설정 확인을 유지하고, 로그인 사용자에게만 개인 Reading·Interview 항목을 표시한다.
- **근거**: 현재 Home은 비로그인 탐색과 로그인 후 이동 대상으로 사용되고 `setup-status`는 같은 View의 HTMX partial이다.
- **검토한 대안**: Home 전체 로그인 요구 또는 개인 허브의 별도 경로 신설. 기존 진입 계약을 불필요하게 바꾼다.

## 결정 2: 기존 Interview 상세로 재진입

- **결정**: Reading과 일대일 Interview 관계를 조회해 상태별로 분류하고, 이어하기는 소유권을 검사하는 기존 Interview 상세 GET에 연결한다. Resume 엔터티는 만들지 않는다.
- **근거**: 기존 상세는 최신 Turn, 확정 답변, 미결정 진행 선택과 첫 질문 전 상태를 판별한다. Interview 생성은 명시적 POST에서만 일어난다.
- **검토한 대안**: 별도 Resume URL·상태 또는 Home GET의 자동 생성. 중복 상태와 부작용을 늘린다.

## 결정 3: 복수 기록과 실제 정보만 표시

- **결정**: 적격 Reading을 상태별 영역에 각각 표시하고 최신 변경 순으로 정렬한다. 실제 도서·상태·진행 단계만 노출한다.
- **근거**: 한 사용자에게 여러 Reading이 가능하며 현재 Home에는 고정 도서·진행률·사색 문구가 있다.
- **검토한 대안**: 영역당 한 기록만 표시하거나 샘플 카드를 유지. 전자는 복귀 경로를 숨기고 후자는 실제 상태와 혼동된다.

## 결정 4: 결정적인 응답·상태 검증

- **결정**: Django test client로 공개/개인 Home, 타 사용자 격리, 카드 링크, 재진입 후 Interview·Turn 불변을 검증한다.
- **근거**: 이 계약은 자동 검증할 수 있고, 프로젝트 헌법은 명시적 요청 없는 실제 브라우저 검증을 필수로 요구하지 않는다.
- **검토한 대안**: 수동 브라우저 확인만으로 완료 판정. 반복 가능한 소유권·무변경 증거를 남기기 어렵다.
